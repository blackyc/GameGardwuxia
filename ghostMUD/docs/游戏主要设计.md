# 游戏主要设计

本文是 `docs/` 中的主设计源。旧设计稿、AI 任务规划、审计日志和迁移记录已归档到 `aidoc/archive_20260707/docs/`，除非人工重新提炼进本文，否则不再作为当前实现依据。

## 项目结构

- `index.html` 是浏览器入口，负责加载样式、运行时数据脚本和 `src/main.js`。
- `src/` 是游戏主要源码，会进入 Vite 打包路径。
- `public/data/` 是运行时数据层，继续以经典脚本注入全局变量，再由 `src/data/data_loader.js` 统一收集。
- `public/ui/` 保存游戏运行时 UI 资源。
- `temp/` 保存临时脚本、调试脚本、一次性执行文件和测试文件，不属于游戏运行路径。
- `aidoc/` 保存历史 AI 文档和过时设计稿，只作追溯参考。

## 世界结构

游戏采用“表层世界 / 夹层世界 / 深层世界”的三层结构。

表层世界是凡人江湖：城门、街巷、药铺、铁匠铺、酒楼、客栈、码头和宗门外门。玩家在这里获得资源、接触 NPC、推进任务和建立身份。

夹层世界是修行者开始感知异常后的世界：同一地点会出现不同描述、隐秘入口、遗物线索和不稳定 NPC 反应。它不是新地图，而是原世界的另一层可见性。

深层世界与灵修、诡异、神祇频率和畸变相关。深层入口不能常驻展示，必须由条件系统控制可见性和可进入性。

## 地图与副本分层

世界地图负责稳定地理节点和常规通行，例如应天府街区、野外道路、宗门区域。

副本房间负责条件化内容，例如特殊二楼、暗格、洞窟、记忆空间、灵修房间和任务空间。副本入口可以挂在世界地图节点下，但副本内部应形成独立层级，避免直接污染主地图的常规出口。

副本房间必须满足以下规则：

- 未满足条件且 `hiddenUntilEligible !== false` 时，不应出现在感知结果中。
- 即使玩家通过旧命令、快速旅行或陈旧 UI 试图进入，也必须由移动服务硬校验。
- 失败时优先显示房间自己的 `fail_msg`。
- 成功进入时可以显示 `success_msg` 作为特殊日志。

## 入口条件

入口条件由 `src/entry_condition.js` 统一判断，供感知和移动同时调用。

当前支持条件：

- `skill`：技能要求。
- `realm`：境界要求。
- `cultivation`：修为要求。
- `daoxin`：道心下限。
- `max_daoxin`：道心上限，用于低心性、诡异或灵修入口。
- `item`：关键物品要求。
- `quest`：任务完成要求。
- `active_quest`：进行中任务要求。
- `faction`：宗门要求。
- `path`：修行路径要求。
- `time`：时辰要求。
- `composite`：`and` / `or` / `not` 复合条件。

新增房间时，条件应写在房间数据上，而不是写在 UI 层或按钮层。UI 只负责呈现结果。

## UI 结构

手机端江湖页采用三块区域：

1. `location-banner`：房间名和顶部远山区域。
2. `jianghu-main-zone`：主描述区，包含场景叙事、人物卡片、互动按钮和展开交互全景。
3. `recent-log`：最近日志区，记录控制台式第三视角事件，例如人物做了什么、感受了什么、系统发生了什么。

主描述区负责“你看见的场景”。最近日志负责“系统记录的发生”。两者不能混写，否则会破坏 MUD 控制台逻辑。

当前背景图仍可采用整图过渡方案。干净背景切图完成后，应将三段背景分别绑定到 `location-banner`、`jianghu-main-zone`、`recent-log`。

## 存档与状态

存档由 `src/core/storage.js` 与 `src/core/save_schema.js` 管理。新增长期状态字段时，必须考虑旧存档迁移、默认值和缺失字段兼容。

## 验收命令

```bash
npm test
npm run build
node temp/work/verify_reachability.cjs
node temp/work/check_missing.cjs
```

每次大版本集成后，除测试和构建外，还需要做桌面与手机端 UI 冒烟检查，确认三块区域、日志区、按钮区、感知展开区没有错位、横向溢出或控制台错误。
