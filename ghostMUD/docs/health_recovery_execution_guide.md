## 2. 文档权威链与冲突裁决

### 2.1 权威优先级

发生冲突时按以下顺序裁决，数字越小优先级越高：

1. 用户在当前任务中明确确认的指令，以及本文件记录的冻结项、范围和验收门禁。
2. 状态为 Accepted 的 ADR：`docs/adr/0001-0004-t7-3-decisions.md`。
3. 项目决策词典：`docs/CONTEXT.md`。
4. 对应领域的最新版专项设计文档，例如身份、教程、战斗数值、状态、装备和 UI v3。
5. `docs/refactor_task_tracker.md` 的任务意图与依赖关系。
6. `overview.md`、旧计划、session 记录、cleanup tracker、`work/` 生成说明等历史材料。
7. 注释、文件名、未验证的完成声明。

`docs/refactor_task_tracker.md` 虽在开头和结尾自称“唯一活文档”，但其最近状态核查停留在 2026-06-24，晚于它的 ADR、`CONTEXT.md` 和本次代码审计已推翻多项状态。因此，它不能继续单独充当完成事实源。

### 2.3 冲突处理规则

- 不得静默选择一份有利于“宣布完成”的文档。
- 先在开发日志的“文档冲突”节列出双方路径、章节和代码事实。
- 若高优先级文档已给出明确答案，按高优先级执行，并把低优先级文档标记为待同步。
- 若同级专项文档互相冲突，停止该冲突点的实现，提交决策建议；可以继续完成不受影响的验证、测试或重构。
- 新决策影响数据兼容、存档、玩家主流程或跨模块接口时，必须新增 ADR，不能只写在开发日志里。

## 3. 状态词典与完成定义

### 3.1 统一状态

所有任务和系统只允许使用以下状态：

| 状态 | 定义 |
|---|---|
| 未开始 | 没有可验证实现 |
| 数据已存在 | 数据文件可加载，但没有主流程消费者 |
| 引擎已存在 | 核心逻辑存在，但默认玩家流程不可达或 UI 不可操作 |
| 可达待验收 | 玩家可进入，但测试、存档、UI 或文档尚未闭环 |
| 已验收 | 满足 3.2 的全部完成条件，并经审计接受 |
| 阻塞 | 存在明确外部依赖或未决设计，日志中有证据 |

禁止使用“基本完成”“差不多完成”“文件已接入所以完成”等模糊说法。

### 3.2 Definition of Done

一个玩家功能只有同时满足以下条件才能标记“已验收”：

1. **设计可追溯**：日志列出实现依据的文档路径和具体章节。
2. **默认可达**：不依赖控制台赋值、手改 state、隐藏 URL 或开发者命令。
3. **玩家可操作**：入口、反馈、失败状态和退出路径在 UI 中存在。
4. **状态可信**：需要持久化的数据可保存、恢复，旧存档处理有定义。
5. **自动验证**：至少有对应的可重复测试或数据校验。
6. **UI 无回归**：通过本文第 6 节的适用矩阵。
7. **文档同步**：状态文档描述的是代码事实，不是预期愿景。
8. **运行清洁**：适用流程无未解释的控制台错误、未处理 Promise rejection、生产 404 或构建警告。

仅加载 70 个技能、8 条经脉、35 个刻印、9 个 Build、32 个 NPC 或 12 个事件，不满足完成定义。一个最小但完整的玩家闭环，优先级高于一整套不可达数据。

## 4. 全局实施规则

1. 一次工作包只处理一个主要风险面。不要在同一工作包里同时重写存档、迁移房间 ID、切换战斗引擎和改 UI。
2. 每项修改先写预期行为和验收项，再改代码；不得靠修改测试去迁就错误实现。
3. 保留经典回合制战斗作为可工作的回退路径，直到新战斗的最小垂直切片被验收。
4. 数据迁移必须同时更新定义、引用、地图、任务、NPC、测试和存档兼容，禁止半迁移。
5. 玩家存档变更必须采用“先读旧、再写新”的迁移策略，禁止通过改 key 逃避兼容。
6. 新抽象必须有实际消费者。`ResourcePool` 这类只实例化、不消费的结构，要么接入并测试，要么明确延期，不得继续计为完成。
7. 所有大版本集成后必须执行 UI 回归门禁。UI 验证不是项目末尾的美化步骤。
8. 当前背景冻结项不得顺手处理；提交中若包含背景图、三段区域透明度、裁切或 CSS 收尾变更，默认判为越界。
9. 不得修改用户或其他工具已经产生、但与本工作包无关的改动。
10. 未运行的命令必须明确写“未运行”和原因，不能写成通过。

## 5. 分阶段健康度恢复路线

阶段必须顺序通过。后续阶段可以做调查和测试准备，但不能越过前置门禁把不可达的大系统接进主流程。

### H0：治理与可复现基线

**目标**：让任何无上下文工具都能在同一环境中启动、构建、知道什么是事实，并能追踪每次变更。

**工作包**：

- 初始化 Git 仓库并建立第一份可信基线提交；若用户另有远程仓库策略，只初始化本地，不擅自推送。
- 建立 `.gitignore`，至少审查 `.tools/`、`dist/`、浏览器 profile、临时日志、截图缓存和编辑器产物。不得忽略源数据、设计文档和验收证据。
- 新增或刷新 `docs/PROJECT_STATUS.md`，只记录经代码和运行验证的状态；`refactor_task_tracker.md` 暂时作为历史任务来源，不直接批量改勾选。
- 记录 Node/npm 版本、启动命令、端口策略和基线构建结果。
- 保存移动端与桌面端基线截图，记录当前已接受的红色标记背景和已知延期项。

**本地运行命令基线**：

```powershell
$env:Path = "$PWD\.tools\node-v24.18.0-win-x64;$env:Path"
node --version
npm.cmd --version
npm.cmd run build
npm.cmd run dev -- --host 127.0.0.1
```

**验收门禁**：

- 新环境按记录命令可启动。
- Git 能显示干净基线，且 `.tools/` 等本地产物不进入版本控制。
- 基线文档不再宣称存档 v3、行功、身份、双修等不可达系统“已完成”。
- 基线截图覆盖 375x812 和 1280x720。

**文档依据**：

- `analysis/project_doc_gap_audit_20260706.md`：“1. 结论摘要”“7. 测试、构建与仓库健康”“8. Grill”。
- `docs/refactor_task_tracker.md`：“1.3 重构进度总览”“6. 验收标准”，但其中完成状态必须重新验证。

**工作包**：

- 处理 `/diagnose.js` 的构建警告和生产 404 风险。诊断脚本若只用于开发，应从生产入口剥离；若确需发布，应成为可打包或明确复制的资源。

- 为已经修复的感知单触发、武学扁平数组、舆图容错、教程自由移动添加回归验证。

**验收门禁**：

- 教程结束后普通移动只执行一次并真正更新 location。
- 寅卯辰、巳午未、申酉戌、亥子丑分别映射到清晨、正午、黄昏、入夜。

**文档依据**：

**目标**：把“人工点过一次”升级为每次集成都能重复执行的反馈回路。

**工作包**：

### H3：数据契约与命名迁移

**目标**：从“脚本都加载了”提升到“结构可验证、引用完整、来源唯一”。

**工作包**：

- 为 LOCATIONS、MAP_POS、MAP_CONN、FACTIONS、NPC_ENCOUNTERS、QUESTS、ITEMS、技能和战诀定义可执行 schema 或结构校验。
- 消除 `index.html` 脚本顺序与 `DATA_MANIFEST` 的双源配置。推荐由一个清单生成/加载，另一处只做校验，不再手工维护两份顺序。
- 先生成 67 个裸房间 ID 的完整映射表，再一次性迁移所有定义和引用。迁移前后房间数、连接数、搜索数据、NPC、任务、地图和存档位置必须可对比。

- “测试通过”但没有命令、退出码和测试数量。
- “UI 正常”但没有视口、页面状态和截图。
- “兼容旧存档”但没有旧样本和字段对比。
- “完成接入”但入口需要控制台改 state。
- “无影响”但没有说明检索范围或回归路径。
- 只贴整段终端输出，不总结失败和关键指标。

## 9. 提交给审计的最小材料包

开发完成后，向审计方提交以下内容：

1. 工作包 ID 和目标。
2. 基线/完成 commit hash；未建立 Git 前提供完整 diff，但 HR-000 后原则上必须使用 commit。
3. `analysis/dev_logs/...` 日志路径。
4. 改动文件列表和 `git diff --stat`。
5. 构建、测试、数据校验的命令与退出码。
6. 适用的四视口 UI 截图及控制台/网络日志。
7. 存档或数据迁移的前后样本。
8. 已知限制、未运行项和希望审计重点检查的位置。

审计结论只使用三档：

- **接受**：范围、行为、测试、UI、数据/存档和文档均满足本工作包门禁。
- **有条件接受**：核心行为成立，仅有明确、低风险、已登记的非阻断项；必须列出补办任务。
- **拒绝**：存在越界、默认不可达、数据/存档风险、UI 回归、测试证据缺失或完成声明失真。

审计重点按以下顺序：

1. 范围是否与工作包一致。
2. 是否遵守文档权威链和具体章节。
3. 默认玩家路径是否真正可达。
4. 是否破坏既有基础旅程、数据或旧存档。
5. UI 三段语义和四视口是否正常。
6. 测试是否会真实失败并返回非零退出码。
7. 文档状态是否忠于代码事实。

## 12. 当前停止线

出现以下任一情况，停止继续扩展并提交日志等待审计：

- 构建或基础 smoke 失败。
- 旧存档可能被覆盖且没有备份/迁移测试。
- 房间或地图引用计数下降但原因不明。
- 江湖三个区域职责混淆、页面重叠、导航失效或控制台报错。
- 为了接入新系统必须手改 state 或依赖控制台。
- 两份同级权威文档冲突且无 ADR 可裁决。
- 工作区出现来源不明且与当前任务冲突的修改。
- 当前红色标记背景或三段布局在无关任务中被改变。

健康度恢复的核心不是“少写代码”，而是让每一次完成声明都能被玩家路径、自动测试、UI 证据、数据契约和文档同时证明。
